# Requirements Analysis: ระบบรับเรื่องร้องเรียนศูนย์ดำรงธรรมจังหวัดศรีสะเกษ (DCMS)
(Project Name: BUGKOShop)

## 1. วัตถุประสงค์ของระบบ (System Objectives)
- เพื่อเป็นศูนย์กลางดิจิทัลในการบันทึกและจัดการข้อร้องเรียนของศูนย์ดำรงธรรมแบบครบวงจร
- เพื่อเพิ่มประสิทธิภาพในการคัดกรอง จำแนก และส่งต่อเรื่องร้องเรียนไปยังหน่วยงานที่รับผิดชอบ
- เพื่อควบคุมและติดตามระยะเวลาการดำเนินงาน (SLA) ไม่ให้ล่าช้า
- เพื่อให้ผู้บริหารมีข้อมูลเชิงสถิติที่ทันสมัย (Real-time Dashboard) สำหรับวิเคราะห์และแก้ไขปัญหาในระดับนโยบาย

## 2. ปัญหาของระบบเดิม (Pain Points of the Old System)
- **การจัดเก็บกระจัดกระจาย:** ข้อมูลมาจากหลายช่องทาง (กระดาษ โทรศัพท์ อีเมล) ทำให้ค้นหายากและสูญหายง่าย
- **การติดตามงานยาก (Poor Tracking):** ไม่ทราบว่าเรื่องร้องเรียนถูกส่งไปถึงไหน หรือติดขัดที่ขั้นตอนใด
- **ความล่าช้า (Delay):** ไม่มีการแจ้งเตือนเมื่อเรื่องใกล้ครบกำหนดเวลา ทำให้เกิดความล่าช้าในการแก้ไขปัญหา
- **ขาดข้อมูลสรุป (Lack of Insights):** ผู้บริหารไม่มีตัวเลขหรือสถิติภาพรวมที่ชัดเจนในการประเมินประสิทธิภาพการทำงานของหน่วยงานอย่างรวดเร็ว

## 3. เป้าหมายของระบบใหม่ (Goals of the New System)
- **รวมศูนย์ข้อมูล (Centralized Data):** ข้อมูลร้องเรียนจากทุกช่องทางต้องถูกรวบรวมไว้ที่ฐานข้อมูลเดียว
- **โปร่งใสและตรวจสอบได้ (Transparency & Traceability):** ทุกขั้นตอนการทำงานต้องมีประวัติ (Log) และสามารถตรวจสอบสถานะได้ตลอดเวลา
- **ทำงานอัตโนมัติขึ้น (Automation):** มีระบบแจ้งเตือนอัตโนมัติเมื่อใกล้ถึงกำหนด (SLA)
- **เห็นภาพรวม (Visibility):** มี Dashboard ที่แสดงข้อมูลสถิติที่เข้าใจง่ายและเป็นประโยชน์ต่อผู้บริหาร

## 4. Functional Requirements
**4.1 การจัดการเรื่องร้องเรียน (Complaint Management)**
- ระบบต้องสามารถบันทึกเรื่องร้องเรียนใหม่ โดยระบุช่องทางที่มาได้ (ได้แก่: มาด้วยตนเอง, โทรศัพท์, หนังสือ, เว็บไซต์, หรือรับโอนจากระบบกลาง)
- ระบบต้องสามารถบันทึกรายละเอียดข้อร้องเรียน (หัวข้อ, หมวดหมู่, รายละเอียด, วันที่เกิดเหตุ, สถานที่เกิดเหตุ)
- ระบบต้องรองรับการแนบไฟล์หลักฐาน (เช่น รูปภาพ, เอกสาร PDF)
- ระบบต้องสามารถสร้างเลขที่รับเรื่องร้องเรียน (Tracking Number) เพื่อใช้อ้างอิงได้

**4.2 การจัดการผู้ร้องเรียนและผู้ถูกร้อง (Parties Management)**
- ระบบต้องสามารถบันทึกข้อมูลผู้ร้องเรียน (ชื่อ-สกุล, เลขบัตรประชาชน, เบอร์โทรศัพท์, ที่อยู่)
- ระบบต้องรองรับกรณี "ไม่ประสงค์ออกนาม"
- ระบบต้องบันทึกข้อมูลผู้ถูกร้องเรียน (ชื่อบุคคล, นิติบุคคล, หรือหน่วยงาน)

**4.3 การส่งต่อและติดตาม (Forwarding & Tracking)**
- เจ้าหน้าที่ศูนย์ดำรงธรรมต้องสามารถ มอบหมาย/ส่งต่อ (Assign) เรื่องให้หน่วยงานที่รับผิดชอบได้
- ระบบต้องให้หน่วยงานที่รับผิดชอบปรับปรุงสถานะ (เช่น รอดำเนินการ, กำลังดำเนินการ, แก้ไขแล้ว, ยุติเรื่อง)
- หน่วยงานที่รับผิดชอบต้องสามารถพิมพ์หรือบันทึกรายงานผลการปฏิบัติงานกลับเข้าระบบได้

**4.4 ระบบแจ้งเตือน (Notification System)**
- แจ้งเตือน (In-app Notification) เมื่อมีเรื่องร้องเรียนใหม่ถูกส่งไปให้หน่วยงาน
- แจ้งเตือนเมื่อเรื่องร้องเรียนใกล้ครบกำหนด SLA หรือ quá hạn (Overdue)
- แจ้งเตือนเจ้าหน้าที่ศูนย์ดำรงธรรมเมื่อหน่วยงานเปลี่ยนสถานะเป็น "แก้ไขแล้ว"

**4.5 รายงานและหน้าปัด (Dashboard & Reporting)**
- แสดง Dashboard สรุปจำนวนเรื่องร้องเรียน โดยแบ่งตามสถานะ, ตามหน่วยงานที่รับผิดชอบ, และตามหมวดหมู่
- สามารถส่งออกข้อมูล (Export) เรื่องร้องเรียนเป็นไฟล์รูปแบบ Excel หรือ CSV สำหรับนำไปทำรายงานภายนอกได้

## 5. Non-functional Requirements
- **Performance:** ระบบต้องมีการตอบสนองที่รวดเร็ว การแสดงผล Dashboard ควรใช้เวลาโหลดไม่เกิน 3 วินาที
- **Usability:** ส่วนติดต่อผู้ใช้ (UI) ต้องรองรับการทำงานทั้งบนจอคอมพิวเตอร์และแท็บเล็ต (Responsive Design) ใช้งานง่าย ไม่ซับซ้อน
- **Security:** รหัสผ่านต้องถูกเข้ารหัส (Password Hashing) การเข้าถึง API ต้องใช้ Authentication (เช่น JWT) และมีการจำกัดสิทธิ์ (Role-based Access Control) อย่างเคร่งครัด
- **Availability:** ระบบต้องสามารถรองรับการใช้งานผ่าน Web Browser ทั่วไปได้ตลอด 24 ชั่วโมง
- **Scalability:** โครงสร้างระบบต้องรองรับจำนวนผู้ใช้งานและจำนวนเรื่องร้องเรียนที่เพิ่มขึ้นในอนาคตได้

## 6. ข้อมูลที่ระบบต้องจัดเก็บ
- **ข้อมูลผู้ใช้ (User Data):** ID, ชื่อ-สกุล, อีเมล, รหัสผ่าน, บทบาท (Role), และหน่วยงานต้นสังกัด
- **ข้อมูลเรื่องร้องเรียน (Complaint Data):** เลขที่รับเรื่อง, หัวข้อ, รายละเอียด, หมวดหมู่, ช่องทางที่มา, สถานะปัจจุบัน, วันที่รับเรื่อง, วันที่กำหนดเสร็จ (SLA)
- **ข้อมูลผู้ร้องเรียน (Complainant Data):** ชื่อ, เลขบัตรประชาชน, ข้อมูลติดต่อ (เว้นแต่ไม่ประสงค์ออกนาม)
- **ข้อมูลผู้ถูกร้อง (Target Data):** ข้อมูลของผู้ที่ถูกร้องเรียน
- **ข้อมูลไฟล์แนบ (Attachment Data):** ชื่อไฟล์, Path/URL, ประเภทไฟล์ (เชื่อมโยงกับเรื่องร้องเรียน)
- **ข้อมูลประวัติการทำงาน (Tracking/Audit Log):** บันทึกว่าใคร เปลี่ยนแปลงสถานะหรือแก้ข้อมูลอะไร เมื่อไร

## 7. ข้อมูลที่ระบบต้องแสดงผล
- **หน้ารายการ (List View):** ตารางแสดงเรื่องร้องเรียน พร้อมระบบค้นหา จัดเรียง และกรองข้อมูล (Filter) ตามสถานะ/หน่วยงาน/หมวดหมู่
- **หน้ารายละเอียด (Detail View):** แสดงข้อมูลครบถ้วนของ 1 เรื่องร้องเรียน พร้อมเส้นเวลา (Timeline) การปรับปรุงสถานะและข้อความรายงานผล
- **หน้า Dashboard:** กราฟ แผนภูมิพาย (Pie Chart) หรือการ์ดสรุปตัวเลขสถิติต่างๆ
- **หน้าจัดการผู้ใช้งาน:** สำหรับ Admin ในการเพิ่ม ลบ หรือแก้ไขสิทธิ์ของเจ้าหน้าที่หน่วยงานต่างๆ

## 8. เงื่อนไขทางธุรกิจของระบบ (Business Rules)
- การรับเรื่องและการคัดกรองเบื้องต้นต้องทำโดยเจ้าหน้าที่ศูนย์ดำรงธรรมเท่านั้น
- หน่วยงานที่รับผิดชอบจะมองเห็นและอัปเดตข้อมูลได้เฉพาะเรื่องร้องเรียนที่ถูกส่งมอบหมายให้หน่วยงานของตนเท่านั้น
- การอนุมัติ "ยุติเรื่อง" (Close Case) ขั้นสุดท้าย อาจถูกจำกัดสิทธิ์ให้ทำได้เฉพาะเจ้าหน้าที่ศูนย์ดำรงธรรม เพื่อให้ตรวจสอบว่าเรื่องนั้นแก้ไขเสร็จสมบูรณ์จริง
- มาตรฐานเวลาดำเนินการ (SLA) จะเริ่มต้นนับจากวันที่เจ้าหน้าที่ศูนย์ดำรงธรรมกดปุ่ม "มอบหมายงาน"

## 9. ข้อจำกัดและข้อควรระวัง
- **PDPA & Privacy:** ข้อมูลผู้ร้องเรียนมีความอ่อนไหว ต้องมีมาตรการไม่ให้หน่วยงานที่ไม่เกี่ยวข้องสามารถเข้าถึงข้อมูลผู้ร้องเรียนของหน่วยงานอื่นได้
- **File Storage:** การใช้ Railway แบบ Ephemeral Filesystem หมายความว่าไฟล์แนบที่อัปโหลดจะหายไปเมื่อ Container ถูกรีสตาร์ท การพัฒนาในระยะยาวต้องเตรียมแผนใช้งาน Object Storage (เช่น AWS S3 หรือ Cloudinary) สำหรับเก็บไฟล์หลักฐาน
- **External Public Portal:** ในระยะแรก ระบบเน้นรองรับ **ผู้ใช้งานภายใน (เจ้าหน้าที่)** เท่านั้น ยังไม่มีฟีเจอร์สำหรับประชาชนทั่วไปในการเข้ามาติดตามเรื่องด้วยตนเองผ่านหน้าเว็บ

## 10. คำถามที่ควรถามผู้ใช้งานจริงเพิ่มเติม (Open Questions)
1. มาตรฐานเวลาดำเนินการ (SLA) ของเรื่องร้องเรียนแต่ละประเภทกำหนดไว้อย่างไร (เช่น 7 วัน, 15 วัน หรือ 30 วัน)?
2. หากหน่วยงานแก้ปัญหาเสร็จแล้ว ใครจะเป็นผู้มีอำนาจตัดสินใจเปลี่ยนสถานะเป็น "ยุติเรื่อง" (เจ้าหน้าที่หน่วยงาน หรือ เจ้าหน้าที่ศูนย์ดำรงธรรม)?
3. ช่องทาง "การนำเข้าจากระบบกลาง" หมายถึงระบบใด มีการเตรียม API ไว้แล้วหรือไม่ หรือเป็นการอัปโหลดไฟล์ Excel เข้ามา?
4. บน Dashboard ผู้บริหารระดับสูงของจังหวัดต้องการดูสถิติเรื่องใดเป็นพิเศษที่สุด (เช่น หน่วยงานที่ค้างงานมากที่สุด)?
